## What is actually useful to Project 51

ThermalForge is a macOS Apple Silicon fan controller and monitor, **not an LLM inference/Metal accelerator**. The CLI's read-only status produces JSON, while the thermal logger produces timestamped thermal.csv (supported SMC sensor keys, actual/target fan RPM, modes), processes.csv (top-five PID/name and an estimated CPU metric), and metadata.json (machine, macOS, ThermalForge version, fan range, keys, sampling rate, start/end/sample count). Source: Sources/ThermalForgeCore/ThermalLogger.swift; Sources/thermalforge/ThermalForge.swift; Sources/ThermalForgeCore/FanControl.swift. The logging CLI supports --rate, --duration, --output, --no-expire, default 1Hz.

This could improve **A/A and A/B validity** for the two distinct 64GB M1 Max MacBooks: monitor ambient/in-machine thermal drift, temperature/fan ramping and cooling-state confounding during native Metal KVarN, QFN original IQ3S, long-context/agent runs, and fused kernel searches. It does **not** itself measure GPU clock, GPU load/power, macOS thermal pressure, unified memory peaks, output correctness, or sustained token rates. Independent powermetrics/macmon/OS telemetry and the real Project 51 harness are still needed.

Evidence: README lists MacBook Pro 16-inch 2021 M1 Max as *Tested*, not either owner's actual unit. Package.swift depends on Swift ArgumentParser and links native Metal for a separate calibration/stress module. GitHub CI workflow runs swift build and swift test on macos-15; code/tests present, but **no executed CI/hardware outcome verified here**. README's claim that default fan curves lose 10–20% performance is **unverified marketing-level generalization**, not a same-machine/QFN measured benefit. Current docs/idle-cpu-experiments.md reports about **4% of one CPU core** for the app at idle on the measured host, with sensor reads about 2.7 percentage points (64%); earlier PR #16's 0.3% result was for a different code path/cadence. Continuous high-rate GUI/controller SMC polling can itself perturb microbenchmarks; low-rate CLI logger is the better initial candidate.

## Reasons to avoid fan control until substantially more validation

1. **Sensor validity [M1 issue #61](https://github.com/ProducerGuy/ThermalForge/issues/61):** a different 2020 M1 MacBook's GPU load raised other keys but not the keys ThermalForge surfaced as GPU; [M4 #63](https://github.com/ProducerGuy/ThermalForge/issues/63) identifies several TG0* keys as battery on M4. On pinned main FanControl.thermalKeys still includes TG0B/TG0H/TG0V as GPU candidates. SafetyPeakTemp takes max over TC/Tp/TG/Tg, not verified model-specific thermal pressure. No proof either owner's M1 Max suffers the same misread, but no reason to trust labels until A/B sensor verification.
2. **Unsafe reset path [open PR #72](https://github.com/ProducerGuy/ThermalForge/pull/72):** actual FanControl.resetAuto() writes fan mode 0 then target 0 and optional Ftst 0, **discards all write success flags** and logs success. If mode reset fails while target zero succeeds, fan can remain stopped in manual mode. The proposed fix is not merged at inspected SHA. Never assume log message proves handback to Apple. Manual SMC Ftst unlock for M1–M4 explicitly suppresses thermalmonitord control during override.
3. **Control races [open PR #76](https://github.com/ProducerGuy/ThermalForge/pull/76), [#77](https://github.com/ProducerGuy/ThermalForge/pull/77), [#73](https://github.com/ProducerGuy/ThermalForge/pull/73):** reports of late in-flight write re-pinning manual after reset/exit, and overly rapid auto release on 100ms transient sensor dips (one reporter logged 2,182 releases in 3 days). Reports are not owner-machine proof, but robust enough to block unattended root fan control.
4. **Threshold issue [open PR #68](https://github.com/ProducerGuy/ThermalForge/pull/68):** other M4-class machines have hotspot readings above 95°C while OS thermal pressure is Nominal, so universal 95°C safety floor pins manual fan speed to max. Do not equate arbitrary SMC key value to active thermal throttling; proposed OS-pressure-primary fix is unmerged.
5. **Release/main gap [issue #71](https://github.com/ProducerGuy/ThermalForge/issues/71):** shipped Homebrew v0.2.3 had daemon SIGPIPE/restart-loop evidence on another machine; October 5 main contains socket hardening. **Do not assume Homebrew formula's release includes the fix**. Root socket daemon increases attack surface and requires explicit audited maintenance. Additional concerns: [open PR #69](https://github.com/ProducerGuy/ThermalForge/pull/69) first manual M1–M4 acquisition misreports timeouts.
6. **Telemetry limits:** Fixed known sensor list, not all physical sensors; process CPU from kinfo_proc is not GPU attribution; no thermal-pressure field in CSV; sensor-key semantics vary by Mac generation, logging overhead and timestamp granularity must be measured.

If not, use macmon/powermetrics instead. Do not allow an unmeasured always-on 100ms monitor into tiny-kernel benches.
